C with TDD · Lesson 1

A red test, then a green one

Vendor Unity, write a Makefile by hand, and watch one assertion fail and then pass. About fifteen minutes, and every later lesson builds on it.

Unity is three files, not a package

There's nothing to install. Unity's core is “a single C file and a couple header files”: unity.c, unity.h and unity_internals.h. You compile them straight into your test program [Getting Started]. Everything else in the repository (Ruby scripts, examples, extras) is optional.

Coming from Go: go test writes main for you and finds every TestXxx. In C with plain Unity, you write main and list each test in it. Unity's Ruby helper can generate that runner, but we'll do it by hand so nothing is hidden.

A Unity test file has four parts, all spelled out in the guide:

  1. #include "unity.h"
  2. setUp() and tearDown(), which run before and after every test. They may be empty, but they must exist.
  3. Test functions: void test_something(void), holding TEST_ASSERT_* macros.
  4. main(): UNITY_BEGIN(), one RUN_TEST(fn) per test, then return UNITY_END();

That last return matters. UNITY_END() returns the number of failed tests, so the process exits non-zero when anything fails, and make (or CI) sees that.

The test executable = Unity + your test file + the code under test, compiled and linked together. One test file → one executable.

Build it

This is where you'll end up. It lives in this workspace under code/hello/, and Lesson 2 keeps growing it.

code/hello/
├── Makefile
├── test/
│   └── test_hello.c
└── vendor/unity/
    ├── unity.c
    ├── unity.h
    └── unity_internals.h

  1. Make the directories and vendor Unity, pinned to the v2.7.0 release so the files never change under you. Run this from the c-tdd/ workspace:

    $ mkdir -p code/hello/vendor/unity code/hello/test
$ cd code/hello
$ for f in unity.c unity.h unity_internals.h; do
    curl -fsSLo "vendor/unity/$f" \
      "https://raw.githubusercontent.com/ThrowTheSwitch/Unity/v2.7.0/src/$f"
  done
$ echo 'build/' > .gitignore

  2. Write the test first, with the wrong expectation on purpose. In TDD you always see red before green, because a test you've never seen fail might not be testing anything.

    test/test_hello.c
    #include "unity.h"

void setUp(void) {}
void tearDown(void) {}

void test_hello_world(void)
{
    TEST_ASSERT_EQUAL_STRING("Hello, world", "Hello, World");
}

int main(void)
{
    UNITY_BEGIN();
    RUN_TEST(test_hello_world);
    return UNITY_END();
}

  3. Write the Makefile. Recipe lines (the indented ones) must start with a real TAB, not spaces. If you get missing separator, that's why. The copy button keeps the tabs.

    Makefile
    CC       := cc
CFLAGS   := -std=c17 -Wall -Wextra -Wpedantic -g
CPPFLAGS := -Ivendor/unity

test: build/test_hello
	./build/test_hello

build/test_hello: test/test_hello.c vendor/unity/unity.c | build
	$(CC) $(CPPFLAGS) $(CFLAGS) $^ -o $@

build:
	mkdir -p $@

clean:
	rm -rf build

.PHONY: test clean
    What do $^, $@ and | build mean?

    $@ is the target being built, and $^ is all of its prerequisites [GNU make: Automatic Variables]. Here that's both .c files. Anything after | is an order-only prerequisite: build/ must exist first, but a change to its timestamp won't force a rebuild [Prerequisite Types]. CPPFLAGS holds preprocessor flags; -Ivendor/unity is what lets #include "unity.h" find the header.

  4. Run make and see red. You should get exactly this (apart from the build lines):

    test/test_hello.c:8:test_hello_world:FAIL: Expected 'Hello, world' Was 'Hello, World' Character 7 Expected 'w' Was 'W'

-----------------------
1 Tests 1 Failures 0 Ignored
FAIL
make: *** [Makefile:6: test] Error 1

  5. Make it green. Change "Hello, World" to "Hello, world" and run make again. You want 1 Tests 0 Failures 0 Ignored and OK.

  6. Break it on purpose. Delete the setUp and tearDown lines and run make. Read the error before you open the next section, and decide which stage of the build complained. Then put the two lines back.

Reading what you just saw

The Unity failure line

PartMeaning
test/test_hello.c:8File and line of the failing assertion. Most editors let you jump straight to it.
test_hello_worldWhich test failed: the function name you gave RUN_TEST.
Expected … Was …The first argument is the expected value, the second is the actual one. Swap them and the message lies to you.
Character 7The zero-based index where the strings first differ. TEST_ASSERT_EQUAL_STRING compares character by character, not by pointer [Assertions Reference].
Error 1make saw a non-zero exit, which is UNITY_END() returning 1 failure.

Step 6: the linker, not the compiler

You should have seen undefined reference to `setUp' from ld. Both of your .c files compiled fine on their own: unity.c only needs to know that setUp is declared somewhere, and unity.h declares it. The error comes when the pieces are linked into one executable and nobody supplied the definition. The guide warns about exactly this: “If your compiler complains that it can't find setUp or tearDown when it links, you'll know you need to at least include an empty function” [Getting Started].

The C refresher hiding in here

cc a.c b.c -o prog does two jobs: it compiles each .c into an object file on its own, then links the object files together. A declaration (in a header) gets you past the compiler. A definition (in some .c file) has to exist for the linker. Go hides this split, and C doesn't. Lesson 2 leans on it when you add hello.h and hello.c.

Check yourself

Without scrolling up, write a complete Unity test file with one test asserting that 2 + 2 equals 4. Use TEST_ASSERT_EQUAL_INT(expected, actual).

#include "unity.h"

void setUp(void) {}
void tearDown(void) {}

void test_addition(void)
{
    TEST_ASSERT_EQUAL_INT(4, 2 + 2);
}

int main(void)
{
    UNITY_BEGIN();
    RUN_TEST(test_addition);
    return UNITY_END();
}

Check: did you put expected first? Did you return UNITY_END(), not just call it?

You write a new test function but forget its RUN_TEST line in main. What happens on make?

  • The test silently never runs
  • The linker reports an error
  • The compiler stops with error
  • Unity finds and runs it

With a hand-written runner, a test exists only if main calls it. Watch the N Tests count: if it didn't go up, your new test isn't running. (-Wall doesn't help here, because the function isn't static, so it never counts as unused.) This is another reason to see every new test fail first.

Your main ends with UNITY_END(); return 0;. One test fails. What does make report?

  • Success; the failure stays hidden
  • Error 1 from failing test
  • A warning about unused values
  • Error 2 from linker step

Unity still prints FAIL, but the process exits 0, so make and any CI pipeline think everything passed. return UNITY_END(); passes the failure count through as the exit status.

In the recipe $(CC) … $^ -o $@, what does $@ expand to?

  • The target's name
  • Every prerequisite listed
  • The first prerequisite
  • All order-only prerequisites

$@ is the target (build/test_hello); $^ is all prerequisites; $< is the first one [GNU make]. Order-only prerequisites are left out of $^, which is why build doesn't end up on the compiler's command line.

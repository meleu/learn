Lesson 1 · C for emulators

The machine is just data

An emulator's variables are the hardware. In this lesson you pick the right C types to hold a CHIP-8: exact-width unsigned integers, an array for RAM, and one struct for everything. By the end you'll have compiled the struct your emulator is built on.

In C, how many bits is an int? Is that guaranteed? And what happens when a signed int overflows?

Usually 32 bits on modern machines, but the standard only guarantees at least 16. Signed overflow is undefined behavior: the compiler may assume it never happens. Both facts push us away from int for hardware state.

1 · What a CHIP-8 is made of

Everything the CHIP-8 "is" fits in a short list. This is from the Specifications section of Tobias Langhoff's guide:

ComponentSize / shape
Memory (RAM)4 KB: 4096 bytes, addresses 0x000–0xFFF
Registers V0–VF16 × 8-bit. VF doubles as a flag register
Index register I16-bit, points into memory
Program counter PCpoints at the current instruction
Stack16-bit return addresses (at least 16 entries)
Delay timer, sound timer8-bit each, count down at 60 Hz
Display64 × 32 monochrome pixels
Keypad16 keys, 0–F

Every row is a number of a fixed width, or a fixed-size array of them. So the job of this lesson is to choose C types whose width matches the hardware exactly.

2 · Exact widths: <stdint.h>

C's classic types only promise minimum sizes. Whether plain char is signed is also left to the implementation (cppreference). For hardware you want the width spelled out, so use the fixed-width types from <stdint.h>:

#include <stdint.h>

uint8_t  vx;   // exactly 8 bits, 0..255      — a register
uint16_t pc;   // exactly 16 bits, 0..65535   — an address

Coming from Go: uint8_t is Go's uint8/byte, and uint16_t is uint16. The names differ, but the idea is the same.

3 · Unsigned wraps, like real hardware

An 8-bit register that holds 255 and gets +1 becomes 0. C gives you this for free with unsigned types: Unsigned integer arithmetic is always performed modulo 2n (cppreference, Overflows). Signed overflow, on the other hand, is undefined behavior. So the rule is simple: all emulator state is unsigned.

uint8_t vx = 0xFF;
vx += 1;        // vx == 0    (wraps, well-defined)

uint8_t z = 0;
z -= 1;         // z == 255  (wraps the other way)

There's a twist that a Go programmer wouldn't expect. Before arithmetic, C promotes anything smaller than int up to int. The expression a + b is therefore computed in full. It only wraps when you store it back into a uint8_t:

uint8_t a = 200, b = 100;
int     sum    = a + b;   // 300  — promoted to int, nothing lost yet
uint8_t stored = a + b;   // 44   — 300 mod 256, truncated on assignment
int     carry  = sum > 0xFF;  // 1 — the carry you'll put in VF

Hold state in unsigned exact-width types so it wraps the way the hardware does. When you need a carry or borrow, compute it from the full-width result before storing it back into 8 bits.

4 · Arrays are memory; a struct is the machine

In C, RAM is just uint8_t memory[4096], and an address is just an index: memory[0x200] is the byte at address 0x200. Programs are loaded there (Memory). A struct collects all the components into one value you can hand around. With a typedef you can drop the struct keyword at every use:

typedef struct {
    uint8_t  memory[4096];   // address == index
    uint8_t  V[16];          // V0..VF
    uint16_t pc;
    /* ...you'll finish this... */
} Chip8;

Check yourself

After uint8_t vx = 250; vx += 10; what does vx hold?

  • 4
  • 260
  • 255
  • -6

260 mod 256 = 4. Unsigned wraps; it doesn't saturate at 255.

With uint8_t a = 200, b = 100; what is int s = a + b;?

  • 300
  • 44
  • 255
  • -56

Both operands are promoted to int before the addition, and the result goes into an int, so nothing is truncated. That's what lets you detect a carry.

Why keep every register and address in an unsigned type?

  • Signed overflow is undefined behavior
  • Unsigned arithmetic is always faster
  • Signed types use more memory
  • Compilers reject signed array indexes

Unsigned arithmetic is defined to wrap modulo 2n. Signed overflow is UB, and the optimizer is allowed to assume it never happens.

At which address does a CHIP-8 program start?

  • 0x200
  • 0x000
  • 0x050
  • 0xFFF

The interpreter itself lived in the first 512 bytes (0x000–0x1FF) on the original COSMAC VIP, so programs start at 0x200. Fonts conventionally sit at 0x050.

Your win: compile the machine

Make a directory for your emulator (say ~/src/chip8) and do the following. Use the table in section 1, not the snippet above. Write it yourself.

  1. Create chip8.h with a complete typedef struct { … } Chip8; covering every row of the table: memory, V, I, pc, stack plus a stack pointer, both timers, display and keypad.
  2. Create main.c. Include chip8.h, declare a static Chip8 c8;, set c8.pc = 0x200;, and print it with printf("pc = 0x%03X\n", c8.pc);.
  3. In the same main, reproduce the 200 + 100 experiment. Predict all three values on paper first, then print them.
  4. Compile with warnings on, and fix every warning: 
    $ gcc -std=c11 -Wall -Wextra -pedantic -o chip8 main.c
$ ./chip8
  5. Bonus: print sizeof(Chip8) with %zu. Add up your fields by hand. Does the total match? If not, ask me why.
Hint: what type for the display?

Simplest is one byte per pixel, uint8_t display[64 * 32];, and that's fine. Packing 8 pixels per byte saves memory but costs bit-fiddling. We don't need that yet.

Hint: what type for the stack pointer?

It only has to index 16 entries, so a uint8_t sp is enough. The stack itself holds addresses, so it's uint16_t stack[16].

Hint: why static?

static gives the variable static storage duration: it's zero-initialized and doesn't live on the stack. A local Chip8 c8; without it would contain garbage, so you'd have to clear it yourself.

Register VX holds 0xF0 and you add 0x20. Write the two C lines that store the wrapped result in VX and set VF to the carry.

int sum = c8.V[x] + 0x20;      // 0x110 = 272, full width
c8.V[x] = sum;  c8.V[0xF] = sum > 0xFF;  // V[x] = 0x10, VF = 1

The order matters, and you'll meet it again in opcode 8XY4. If X is F, writing VX first and then VF would clobber the result, so the flag gets written last.

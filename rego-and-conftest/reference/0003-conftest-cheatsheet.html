Conftest Cheat Sheet

The contract, the flags, the exit codes. Verified against conftest (dev build, OPA 1.19.0) on this machine.

Conftest adds no language. It parses a file into input, runs your Rego, reads data.<namespace>.deny and .warn, and turns the result into an exit code. Everything below is that sentence in detail.

The contract

ConventionDefaultOverride
Policy location./policy/, searched recursively-p, --policy
Package (the namespace) †main-n, --namespace; --all-namespaces
Failing rule namesdeny, violationnone; _suffix allowed (deny_replicas)
Non-failing rule namewarn--fail-on-warn makes it fail
What input isone parsed document, evaluated alone--combine (see below — it changes input's shape)
Message typea string in the setan object with a msg key

Commands

Flags worth knowing

FlagDoes
-p, --policyPolicy directory. Default policy. Repeatable.
-n, --namespacePackage to query. Default main. Supports globs: -n 'k8s.*'.
--all-namespacesQuery every package found. The escape hatch when 0 tests surprises you — cures a wrong package name, but not a wrong rule name.
--fail-on-warnExit 1 for warnings too. Turns warn into a blocking gate.
--no-failAlways exit 0. For reporting-only pipeline stages.
-o, --outputstdout (default), json, tap, table, junit, github, azuredevops, sarif.
--parserOverride format detection. See the parser list below.
--combinePass all documents at once, as an array of {"path", "contents"} objects. Rewrites input — rules written for single documents will not match.
--dataLoad JSON/YAML as data.* — the mechanism behind exception lists.
--traceFull evaluation trace on stderr. The conftest version of opa eval --explain full.

Reading the report

You seeIt means
N testsRule evaluations: rules × parsed documents. Not files, not assertions.
0 tests †Policies loaded and compiled, but nothing was found at the queried address — a package that is not main. Exits 0. (A missing or empty -p directory, or a Rego syntax error, is a different case: conftest errors and exits 1.)
N passedRules that contributed no member. Includes rules whose key was undefined — see the silent pass.
1 warningA warn rule fired. Does not affect the exit code without --fail-on-warn.
0 exceptionsDenials suppressed by an exception rule; those lines print as EXCP. An exception names a rule suffix, so ["replicas"] excepts deny_replicas.

Exit codes

SituationExit
No failures0
Warnings only0 — or 1 with --fail-on-warn
Any deny/violation fired1 — but 2 with --fail-on-warn
No rules found (0 tests) †0 — the dangerous one
Policy dir missing or empty1, with an Error: on stderr
Rego syntax error1, with rego_parse_error
Anything, with --no-fail0

--fail-on-warn renumbers everything, it does not just add a case. Without it: warnings 0, failures 1. With it: warnings 1, failures 2. So a pipeline step that reads exit 1 as “the policy denied something” starts meaning “the policy warned about something” the day somebody adds the flag, and real denials become the code nothing is checking for. Key CI on the report, not on == 1.

The two silent passes †

Both look like a green pipeline

A · The key is absent. input.metadata.namespace on a manifest with no namespace: is undefined, so the body cannot hold, so the rule contributes nothing — reported as passed. If absence matters, write the not rule too.

B · The package is not main. Conftest queries data.main.deny and finds nothing there. Reported as 0 tests, 0 passed, exit 0. The count is the tell — make CI reject 0 tests.

This is the only silent misconfiguration. A missing policy directory, an empty one, and a Rego syntax error all exit 1 on their own. So the single thing your CI has to add is a check that rules were actually evaluated.

Making CI reject 0 tests †

There is no built-in flag for this. --strict is Rego's compiler strictness, not this; --fail-on-warn only promotes warnings. --all-namespaces is the nearest thing and it is not a substitute: it cures a wrong package name, but a policy whose rules are named anything other than deny/violation/warn still reports 0 tests and exits 0 under it. Verified. So the two are complements — run with --all-namespaces if you like, and still add the check yourself. Both recipes below were verified on this machine against six cases: violating file, clean file, wrong package, empty policy dir, missing policy dir, and a Rego syntax error.

Which one

Recipe 1 in every pipeline — it is three lines and answers "did the gate run?".

Recipe 2 as well, once the policies matter enough that someone might quietly weaken one. It answers the stronger question: "does the gate still bite?" The canary is a config file, so it costs nothing to keep and it fails loudly the day a refactor stops matching.

The check underneath both is unit-testing the policy itself with opa test / conftest verify. That is a lesson of its own — these two recipes guard the wiring, not the logic.

Parsers available in this build

Detected from the file extension, or forced with --parser.

cue · dockerfile · dotenv · edn · hcl1 · hcl2 · hocon · ignore · ini · json · jsonnet · nginx · properties · spdx · textproto · toml · vcl · xml · yaml

FormatShape of input
YAML / JSONThe document as an object. Multi-document YAML gives one input per document.
Dockerfile †An array of instruction objects with keys Cmd, Value, Flags, Stage, SubCmd. Cmd is lowercased ("from", "user"). Rules must iterate, not address fields.
XML / pom.xml †Nested objects; attribute-free elements collapse to strings. Gotcha: one <dependency> becomes an object, two or more become an array.

When a format is not in this table, do not guess — conftest parse it and read the JSON. That command is what makes any unfamiliar format tractable.

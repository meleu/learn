Rego Builds a JSON Document

You already had the right instinct. This lesson makes it precise, gives it the official vocabulary, and hands you the one command that lets you watch it happen.

Your win for this lesson

By the end you can explain to a coworker why Rego exists, describe a .rego file as rules that build a JSON document from input data, and run a policy locally with opa eval to read the document it produced.

You wrote this in your old notes:

Your prior model

Rego is a language to build JSON documents. A .rego file has rules that build a JSON document based on input data (also JSON).

That is not a simplification you should outgrow. It is the model the OPA authors designed around, and everything else in this course hangs off it. What it is missing is only its vocabulary and its proof — the command that shows you the document.

1 · Why Rego exists at all

Every system already makes policy decisions: is this user an adult? can they delete that resource? does this image come from a trusted registry? The old way is to bury those decisions inside each application — scattered across repos, inconsistent, and impossible to change without a redeploy.

OPA's founding claim is that this is backwards. Policy should be decoupled from the software that enforces it: "specified declaratively, updated at any time without recompiling or redeploying, and enforced automatically."¹ The people who own the rule should be able to read, write, version and audit it without touching the system that obeys it.

Decision versus enforcement. Rego decides ("this is not allowed"). The calling system enforces ("so I will reject it"). Rego never blocks, deletes or deploys anything itself — it only ever computes a value.

This is the framing to lead with when you brief your team. Not "we're adding a linter" but "we're moving rules out of people's heads and out of scattered scripts, into one place you can read, version and test."

That decoupling only works if the engine is domain-agnostic — it cannot know what a Deployment or a pom.xml is. So OPA reduces every domain to the one shape they all share: structured data in, structured data out. Rego is a language for reasoning about that data. Not about Kubernetes. About JSON.

2 · What a .rego file actually is

Here is the thing most newcomers get wrong. A .rego file is not a script that runs top to bottom doing things. It is a set of declarative rules that build a JSON document. You hand OPA some JSON; it evaluates your rules; it hands a JSON document back.

input
the JSON you are asking about
{"age": 21}
→
rules
your .rego definitions
→
a JSON document
what the rules built
{"allow": true}

The docs say it in exactly these terms: rules "define the content of virtual documents… When OPA evaluates a rule, OPA generates the content of the document that is defined by the rule."² A "decision" is not a special kind of thing. It is just a value sitting somewhere in the JSON document your rules built.

Everything OPA knows lives in one JSON tree. Two roots matter today:

RootWhat lives there
input The data for this question, handed in by the caller at query time. Exactly one per evaluation.
data Everything else: context you pre-load (a legal minimum age, a list of approved registries) plus the documents your rules generate. Your policy's output lives here.

A Rego policy decides a request is not allowed. What happens to the request?

  • Nothing, until a caller enforces it
  • Rego blocks it inside the engine
  • Rego reverses it and restores state
  • Rego returns it to the sender
Rego computes a verdict from the data it is given. Acting on that verdict — rejecting the request, failing the pipeline — is the caller's job. This separation is the whole point of OPA.

4 · The one subtlety: undefined is a missing key

Change age to 16 and ask for the whole document again. Predict the answer before you read on.

An empty document. The body input.age >= 18 could not be satisfied, so the rule contributed nothing at all — the allow key simply is not there. Rego calls this state undefined, and structurally it means exactly "this key is absent from the document."

Flag this one for your coworkers

Undefined is not false, and not null. Those are real values that are in the document. Undefined is the absence of a key. Anyone arriving from Python or Go will assume a failed condition yields false; in Rego it yields nothing at all. This is the single most common source of a policy that quietly does nothing.

For {"age": 16}, with only the allow if rule above, the allow key is…

  • absent — the rule added nothing
  • present, holding the value false
  • present, holding the value null
  • present, holding an empty object
An unsatisfied body contributes no value, so the key never appears. That is why the whole document came back as {}. Absence, not falsity.

default supplies a value for when no other definition of that rule fires. Being a constant rather than a conditional, it needs no if. The key is now always present, and callers never have to reason about undefined.

What does adding default allow := false change for {"age": 21}?

  • Nothing — the rule still fires
  • The document now holds false
  • The two values are both kept
  • Evaluation fails with a conflict
A default is only consulted when every other definition of the rule is undefined. At 21 the body is satisfied, so allow is true and the default is never reached.

Two honest asterisks on "it is all JSON"

(1) It is the JSON data model, not literal JSON text. Your input need not be a .json file — later, other tools will parse YAML, Dockerfiles and XML into the same tree. Rego also adds one type JSON lacks: sets, which you will build in the next lesson and which OPA serialises to arrays on output.

(2) undefined is the one thing that is not a value — it is the absence of a key, as you just saw. Everything else OPA produces is ordinary JSON.

6 · The tools, for now

ToolWhat it is for
opa The engine, and your only tool for the next few lessons. opa eval evaluates any path in the document; opa fmt formats to current syntax; opa test unit-tests policies.
Rego Playground Browser REPL. Paste policy and input, see the document instantly. Nothing to install, and the fastest way to share a snippet with a coworker or with a forum.

You already have opa installed, at version 1.19.0. Confirm with opa version.

Where conftest fits — later. Conftest is a thin wrapper that runs OPA for you: it parses config files into input and applies a naming convention on top. It is your eventual pipeline tool, and it is just OPA underneath. We are deliberately leaving it alone until the Rego fundamentals are solid — learning the wrapper before the engine is exactly how people end up copy-pasting policies they cannot debug.

Syntax note — you are on Rego v1

Since OPA 1.0, if before a rule body is required syntax (constants like default allow := false need none).³ A great deal of pre-2024 material online omits it. When a snippet from a blog fails, suspect its age before you suspect yourself — the error is unmistakable:

rego_parse_error: `if` keyword is required before rule body

Check yourself

Which command prints the whole JSON document that policy.rego builds?

  • opa eval -d policy.rego -i input.json 'data.example'
  • opa check policy.rego --with input.json 'example'
  • opa run policy.rego --input input.json 'example'
  • opa test policy.rego --input input.json 'example'
opa eval evaluates a path. -d loads the policy, -i supplies input, and the query data.example is the node your package writes into — so OPA prints the document it built there.

In one sentence each: what does a .rego file do, and what does opa do with it?

A .rego file is a set of rules that build a JSON document out of input data. opa loads those rules, feeds them an input, evaluates the document, and lets you query any path within it.

If your sentences said "checks" or "validates", nudge them toward "builds". Validation is something a caller does with the document afterwards — decision versus enforcement.

Terminal drill

Ten minutes, opa only. The point is not the typing — it is steps 4 and 5, where you watch a key disappear and then come back.

  1. Make a scratch directory beside your other exercises, and confirm your version is 1.0 or later. (Run this from the workspace root; it will not touch anything you already have in exercises/.)

    mkdir -p exercises/001-mental-model && cd exercises/001-mental-model
opa version

  2. Write the policy and the input. Type them rather than pasting — the muscle memory for if is worth twenty seconds.

    cat > policy.rego <<'EOF'
package example

allow if input.age >= 18
EOF

echo '{ "age": 21 }' > input.json

  3. Print the whole document, then one node of it. Notice that the first is an object and the second is a bare value.

    opa eval -d policy.rego -i input.json 'data.example' --format pretty
opa eval -d policy.rego -i input.json 'data.example.allow' --format pretty

  4. The one that matters. Set the age to 16 and print the document again. Say out loud what happened to the key, and why it is not false.

    echo '{ "age": 16 }' > input.json
opa eval -d policy.rego -i input.json 'data.example' --format pretty
opa eval -d policy.rego -i input.json 'data.example.allow' --format pretty

  5. Add the default line to policy.rego, keeping the age at 16, and re-run. The key is back — now holding a real value.

    cat > policy.rego <<'EOF'
package example

default allow := false

allow if input.age >= 18
EOF

opa eval -d policy.rego -i input.json 'data.example' --format pretty

  6. Now query one level higher — the root of the tree — and see where your package sits inside it. Predict the shape before you run it.

    opa eval -d policy.rego -i input.json 'data' --format pretty

  7. Finally, break it on purpose. Write the rule the way a 2022 blog post would, with no if, and read the error carefully — you will meet it again.

    printf 'package example\n\nallow {\n\tinput.age >= 18\n}\n' > old.rego
opa eval -d old.rego -i input.json 'data.example' --format pretty

Main takeaways

  • Policy decoupling is the reason Rego exists: pull decisions out of application code into a versioned, testable engine.
  • Decision versus enforcement. Rego computes a verdict; the caller acts on it. Rego never blocks, deletes or deploys.
  • A .rego file is not a script — it is rules that build a JSON document from input.
  • Everything lives in one tree: input (this question's data) and data (loaded context plus what your rules generate).
  • Undefined is a missing key. An unsatisfied body adds nothing, so the key is absent — not false, not null.
  • default supplies a fallback so the key is always present.
  • The core loop: edit input → re-run → read the document.

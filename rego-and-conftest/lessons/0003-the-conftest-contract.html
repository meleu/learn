Rego & Conftest · Lesson 3

The Conftest Contract

Conftest adds no language. Everything it runs is the Rego you already know from lesson 2. What it adds is four conventions — and a policy that breaks any one of them fails silently, by passing.

Your win for this lesson

By the end you can write a real conftest policy for a Kubernetes Deployment, read its output precisely enough to know what was counted, and recognise the two ways conftest reports success on a file it should have rejected.

1 · First, your file becomes input

Start from the file you would actually be checking at work.

Rego does not read YAML. So the first thing conftest does is turn that file into the JSON document your rules will address — and it will show you exactly what it produced:

conftest parse is the most useful command in the tool. It answers the only question that matters when you start writing rules for an unfamiliar file: what does input actually look like? Never guess a path — parse first.

That JSON becomes input. Your rules build a document from it, exactly as in lesson 2. Then conftest reads two keys out of that document — and nothing else.

That is the whole of it. Once you have written a policy we will run conftest's query by hand with opa eval and get the identical result, which is the proof that no new language is involved — but the policy has to exist first.

2 · The four conventions

Because conftest has to find your rules without being told where they are, it fixes four things by convention. Each has a flag that overrides it, and each is a way to fail silently if you get it wrong.

ConventionDefaultOverride
Where the policy lives a directory named policy/, searched recursively -p, --policy
Which package it declares † package main — conftest calls this the namespace -n, --namespace, --all-namespaces
What the rule is called deny, violation (a synonym), warn none — but a _suffix is allowed: deny_replicas
What input is one parsed document, evaluated on its own --combine (a later lesson)

The docs state the first three plainly: "Conftest looks for deny, violation, and warn rules. Rules can optionally be suffixed with an underscore and an identifier, for example deny_myrule"¹; policies "by default should be placed in a directory called policy"¹; and "by default, Conftest looks for these rules in the main namespace"¹.

The sentence to put on the whiteboard

Conftest is not a policy engine. It is a file reader and an exit code wrapped around opa eval, plus an agreement about what your rules are called.

Everything your coworkers need to learn to write policies is Rego. Everything they need to learn to run them is the table above.

3 · A Deployment policy

Three rules, in policy/deployment.rego. There is nothing here you have not seen: each is a partial set rule with a one-expression body.

Line by line, in the vocabulary you already have:

  • package main — convention 2. Not a description of the file; the address conftest will look at.
  • deny contains "…" — a partial set rule whose member is a literal string. The message is the member.
  • not input.metadata.labels.owner — lesson 2's absence check, on a nested path. It holds when any link in that chain is missing.

One thing this policy does not do

Nothing here checks input.kind == "Deployment". The policy assumes every file it is handed is a Deployment — hand it a Service and the replicas rule quietly contributes nothing. That is fine for today (the point is the contract, not the rule set), but a real repository mixes kinds in one directory, so a production policy opens with a kind guard. Guarding needs a two-expression body, which is the next lesson.

4 · Run it, and read the count carefully

"3 tests" is three rules, not three files. Conftest counts rule evaluations: three rules against one document. Give it a two-document YAML and the same policy reports six:

That is convention 4 made visible: each YAML document is its own input, evaluated independently. Your rules never see the file as a whole, and never see two documents at once — so a rule cannot say "this Deployment needs a matching Service". (That is what --combine is for, later.)

conftest test reports 3 tests for a single file. What was counted?

  • Rules found in that namespace
  • Fields checked in that document
  • Errors raised during that run
  • Lines of Rego in policy
Conftest counts rule evaluations — every deny and warn rule in the namespace, once per parsed document. Three rules against two documents reports six.

5 · deny and warn differ in exactly one thing

Fix the namespace and the replicas but leave the label off, and only the warn rule fires:

Same Rego, same set, same evaluation. The only difference between deny and warn is which one conftest turns into a non-zero exit code — which is to say, the only difference is whether the rule blocks a merge. And even that is a caller's choice:

Lesson 1's decision-versus-enforcement split, now with a name attached. deny and warn are two decisions your policy publishes. Turning a decision into "this merge is blocked" is done by conftest's exit code and the flags the pipeline passes — not by the rule.

A file triggers one warn and no deny. What exit code does conftest test return?

  • Zero, because warnings never fail
  • One, because warnings always fail
  • Zero, unless the rule matched
  • One, unless the file parsed
Warnings are reported and ignored by the exit code, so a pipeline keeps going. Pass --fail-on-warn if you want them to block instead.

6 · Two ways to pass a file you should have failed

This is the section to remember, and the one to walk your coworkers through. Both failures look identical from the outside: exit 0, green pipeline, broken config shipped.

Trap A — the key isn't there

Kubernetes lets you omit namespace: from a manifest. Delete that one line from the failing Deployment and give conftest everything else it wanted:

You met this in lesson 2 and here it is wearing work clothes. input.metadata.namespace is undefined, so the comparison is undefined, so the body does not hold, so the rule contributes no member — and contributing nothing is indistinguishable from finding nothing wrong. Worse: a manifest with no namespace does land in default when applied, so this is a real violation the policy waved through.

Trap B — the package isn't main

Now rename the package to something more descriptive, which is exactly what a careful person does when the policy directory starts filling up:

Conftest queried data.main.deny, found nothing at that address, and correctly reported that no rules had anything to say. The policy is fine. The rules are fine. They were never asked.

Flag this one for your coworkers

The tell is 0 tests. A passing run reports the number of rules it evaluated; a run that found no rules reports zero and exits 0 just the same. Teach people to read the count, not the colour. Any CI job running conftest should fail on 0 tests, because that number means the gate was never closed.

Two ways out, both fine:

Until you have a reason to split namespaces, package main everywhere is the boring, correct answer.

Your policy declares package kubernetes. You run conftest test deploy.yaml with no flags. What happens?

  • Nothing is tested and it passes
  • Every rule runs and it passes
  • Nothing is tested and it fails
  • Every rule runs and it fails
Conftest looks only at data.main unless told otherwise. It finds no rules there, reports 0 tests and exits 0 — the most dangerous green you will see.

The Deployment YAML has no namespace: key at all. The namespace rule…

  • adds nothing, so the file passes
  • adds its message, so it fails
  • raises an error about the key
  • adds nothing, so the run errors
An absent key makes the comparison undefined, the body cannot hold, and the rule contributes no member. If absence matters — and here it does — write the not rule for it as well.

A coworker messages you: "I wrote a deny rule, the config definitely breaks it, but conftest says 0 tests, 0 passed and exits 0. Is conftest broken?" Diagnose it in three sentences, and say how they should have caught it.

Conftest only queries data.main.deny by default, so a policy declaring any other package is never looked at — 0 tests means "no rules found at that address", not "no problems found". Either rename the package to main or pass -n <their-package>.

The habit that catches it: read the count on every run, and make CI reject 0 tests outright.

If your answer began with the policy directory rather than the package, that is the other half of the same trap — an empty or misnamed policy/ produces exactly the same 0 tests.

Terminal drill

Twelve minutes. Steps 6 and 7 are the ones that matter — they are the two silent passes, and you want to have caused them both yourself before a coworker causes one for you.

  1. New exercise directory, with the policy directory conftest expects. Run from the workspace root.

    mkdir -p exercises/003/policy && cd exercises/003

  2. A Deployment that breaks all three rules.

    cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  namespace: default
spec:
  replicas: 1
EOF

  3. Look before you write. Get in the habit of parsing first, every time you meet a new file format.

    conftest parse deployment.yaml

  4. The policy. Type it — package main and deny contains are the two things you want in your fingers.

    cat > policy/deployment.rego <<'EOF'
package main

deny contains "Deployment must not run in the default namespace" if input.metadata.namespace == "default"

deny contains "Deployment must have at least 2 replicas" if input.spec.replicas < 2

warn contains "Deployment is missing the owner label" if not input.metadata.labels.owner
EOF

conftest test deployment.yaml; echo "exit=$?"

  5. Prove there is no magic. Do conftest's job with the lesson-2 toolchain and confirm you get the same two sets.

    conftest parse deployment.yaml > deployment.json
opa eval -d policy/deployment.rego -i deployment.json 'data.main' --format pretty

  6. Trap A. Delete the namespace: line, satisfy the other two rules, and watch a namespace policy approve a manifest with no namespace.

    cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    owner: meleu
spec:
  replicas: 3
EOF

conftest test deployment.yaml; echo "exit=$?"

  7. Trap B. Restore the violating file, rename the package, and read the count. Predict the exit code before you run it.

    printf 'apiVersion: apps/v1\nkind: Deployment\nmetadata:\n  name: hello\n  namespace: default\nspec:\n  replicas: 1\n' > deployment.yaml
sed -i 's/^package main/package kubernetes.deployment/' policy/deployment.rego

conftest test deployment.yaml; echo "exit=$?"
conftest test --all-namespaces deployment.yaml; echo "exit=$?"
sed -i 's/^package kubernetes.deployment/package main/' policy/deployment.rego

  8. Exit codes. Get the file down to a warning only, then make the warning block.

    printf 'apiVersion: apps/v1\nkind: Deployment\nmetadata:\n  name: hello\n  namespace: team-a\nspec:\n  replicas: 3\n' > deployment.yaml

conftest test deployment.yaml; echo "exit=$?"
conftest test --fail-on-warn deployment.yaml; echo "exit=$?"

  9. One input per document. Append a second Deployment to the file and explain the new count out loud before reading it.

    printf -- '---\napiVersion: apps/v1\nkind: Deployment\nmetadata:\n  name: bye\n  namespace: default\nspec:\n  replicas: 1\n' >> deployment.yaml

conftest test deployment.yaml

  10. Now yours — no snippet given. Add a deny rule requiring an app label, and a second rule that catches trap A: fail a Deployment that declares no namespace at all. Confirm both fire. (Ask me if either fights back.)

Main takeaways

  • Conftest adds no language. It parses a file into input, runs your Rego, reads deny/warn, and returns an exit code.
  • Four conventions: policy in policy/, package main, rules named deny/violation/warn (_suffix allowed), and input is one document at a time.
  • conftest parse FILE shows you the JSON your rules will address. Parse before writing rules, always.
  • The report counts rule evaluations: rules × documents, not files.
  • deny and warn are the same mechanism; only the exit code differs, and --fail-on-warn changes even that.
  • Two silent passes. A missing key makes a rule contribute nothing; a non-main package makes conftest find no rules at all. The second announces itself as 0 tests — fail your CI on that.

Rego & Conftest · Lesson 6 · Practice

Translate the Requirements

No new syntax on this page. A platform team has written seven rules in plain English, and six Kubernetes manifests are sitting in a directory breaking some of them. Your job is the one you will have at work: turn the English into Rego, and prove the Rego catches what it should.

Your win for this lesson

One policy/ directory that enforces all seven requirements, confirmed line by line by an automatic checker — including the requirements that are easy to get almost right.

1 · What is already on disk

Everything lives in exercises/006/. You write only policy/.

The table deliberately says nothing about what is wrong with each file. Finding that out is what your policies are for.

2 · The one convention, and the feedback loop

Every message you produce must start with the requirement's ID in brackets. The rest of the wording is yours:

The ID is also what check.sh keys on. It runs conftest test over manifests/ and compares, per requirement, which file got how many messages at which level (FAIL or WARN) against an answer table. Pass IDs to check only those; pass nothing to check everything.

check.sh contains its answer table in plain text. It tells you where the violations are, never how to write a rule that finds them — reading it first is like reading a test suite before writing the code. Your call; the practice is the same either way.

3 · The loop for every requirement

The same four moves each time, all from earlier lessons. Do not skip the first two just because the requirement feels obvious — the ones that feel obvious are where the silent passes live.

  1. Look at the shape of the file the requirement is about: conftest parse manifests/<file> (lesson 3). Never guess a path.
  2. Ask the question as a query before writing a rule: opa eval -i manifests/<file> '…' --format pretty (lesson 5 §3). The rule body is that query.
  3. Write the rule in policy/, package main, message starting with the tag.
  4. Run ./check.sh K8S-NN. Green for that ID means move on; anything else means go back to move 1, not to the rule.

4 · The requirements

Roughly easiest first. Each hint points at the lesson that holds the idea, not at the answer — open one only after you are stuck.

  1. Set up. From the workspace root, run the checker before writing anything, and read its complaint.

    cd exercises/006
ls manifests
./check.sh
mkdir policy

  2. K8S-01 · Exposed Services

    A Service of type NodePort or LoadBalancer exposes a workload outside the cluster. That is sometimes intended, so it should be flagged for review but must not block the pipeline.

    WARN Applies to: Services · Message names: the Service and its type

    Hint

    "Flag but don't block" is a choice of rule name (lesson 3 §5). "One of two values" is the shortest OR spelling in lesson 4 §6.

  3. K8S-02 · Namespaces

    Every resource must declare its namespace explicitly, and that namespace must not be default.

    FAIL Applies to: every kind · Message names: the kind and name of the resource

    Hint

    That sentence contains two ways to break it, joined by "and" in English — but a manifest breaks it if it does either thing, so in Rego it is an OR (lesson 4 §4). When you write the message for the missing case, ask what every value you interpolate evaluates to (§3 of the same lesson).

  4. K8S-03 · Replicas

    Deployments and StatefulSets must run at least two replicas. Kubernetes defaults an omitted replicas field to 1¹, so leaving it out is a violation too.

    FAIL Applies to: Deployments and StatefulSets · Message names: the kind and name

    Hint

    What does input.spec.replicas < 2 evaluate to when the key is not there (lesson 3 §6)? And once you handle the missing case, make sure a Service — which has no replicas either — is not dragged in (lesson 4 §2).

  5. K8S-04 · Floating image tags

    No container may use an image tagged :latest. The tag moves, so the same manifest can deploy different code on different days².

    FAIL Applies to: every container in a Deployment, StatefulSet or Pod · Message names: the resource, the container and its image

    Hint

    You wrote this rule in lesson 5. What is new is the Pod: run conftest parse on it and compare where its containers live. Two paths to the same kind of thing is an OR, and lesson 4 §6's helper-rule spelling can collect from both — a helper can be a set built with contains (lesson 2), not only a true/false.

  6. K8S-05 · Memory limits

    Every container must set a memory limit (resources.limits.memory)³.

    FAIL Applies to: every container in a Deployment, StatefulSet or Pod · Message names: the resource and the container

    Hint

    Bind first, negate second (lesson 5 §7). If you built a container helper for K8S-04, this rule should be three lines of body.

  7. K8S-06 · Privileged containers

    No container may run privileged (securityContext.privileged: true)⁴.

    FAIL Applies to: every container in a Deployment, StatefulSet or Pod · Message names: the resource and the container

    Hint

    One manifest sets privileged explicitly to false. Make sure your rule is asking about the value, not about whether the key exists.

  8. K8S-07 · Readiness probes (stretch)

    A workload in which no container defines a readinessProbe will receive traffic before it is ready⁵. One probed container is enough — this is a judgement about the workload, not about any single container.

    WARN Applies to: Deployments and StatefulSets · Message names: the kind and name

    Hint

    "About the collection as a whole, no single member at fault" is how lesson 5 §8 describes the one job every is for. There is also a spelling with some in a helper and a not in the rule — try both and keep the one you would rather explain.

  9. All green. Run the whole table, then look at the raw report once so you have seen what a coworker's pipeline would print.

    ./check.sh
conftest test manifests/; echo "exit=$?"

5 · Debrief

Several of these requirements had a version that looks correct, compiles, and reports a clean pass on a file that breaks the rule. For each one you can name, say which file would have slipped through and which silent pass from the course it was. Then name one manifest that would break a requirement and still get past your policy — something check.sh never tests.

K8S-02, missing namespace — api.yaml. Interpolating input.metadata.namespace into the message for the missing case hands sprintf an undefined value, which kills the body (lesson 4, silent pass 3).

K8S-03, omitted replicas — api.yaml. input.spec.replicas < 2 on a missing key is undefined, not true, so a rule with only the comparison never fires on the manifest that is most wrong (lesson 3, silent pass 1). Adding the missing case without a kind guard fails the other way — loudly, on both Services and the Pod — which is what the ✗ expected 0 lines are for.

K8S-04, 05, 06 on the Pod — debug-pod.yaml. A rule iterating only spec.template.spec.containers iterates nothing on a Pod: zero bindings, clean pass (lesson 5, silent pass 4). K8S-06 shows it most starkly, because the Pod is its only violation — so a Deployment-only rule produced the · line, indistinguishable from not having written it.

K8S-06, existence instead of value — the mirror image, not a silent pass: testing c.securityContext rather than privileged == true wrongly denies worker.yaml.

A gap no test here covers: an image with no tag at all, such as nginx. Kubernetes treats it as :latest², and endswith(c.image, ":latest") lets it straight through. Closing that needs a built-in this course has not used yet — worth asking about.

A requirement is not translated until you have watched it fail on the file that breaks it and stay quiet on the file that does not. Every trap above was caught by one half of that sentence — which is why worker.yaml, the manifest that breaks nothing, is in the directory at all.

Main takeaways

  • Parse, query, rule, check — in that order, every time. The shape comes from conftest parse, never from memory.
  • English "must be present and must not be X" is Rego OR: two ways to violate it, so two definitions.
  • When a field has a default, omitting it is a violation you must write separately. A comparison against a missing key is undefined, not true.
  • The same kind of thing at two paths (a Pod's containers vs a Deployment's) is an OR, and a contains helper can collect from both.
  • A fixture that breaks nothing is as important as the ones that break everything: it is the only thing that catches a rule firing where it should not.
  • Tag each message with a requirement ID. It makes a failing pipeline traceable to a written rule, and makes results countable per requirement.

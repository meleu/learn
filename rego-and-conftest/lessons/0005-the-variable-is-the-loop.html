Rego & Conftest · Lesson 5

The Variable Is the Loop

Real config is full of lists — containers, ports, volumes, dependencies — and you cannot reach a list element with a path. Rego's answer is not a loop. It is a variable, and an engine that finds every value the variable could take. Once you see that, iteration stops being a construct you memorise.

Your win for this lesson

One rule that inspects every container in a Deployment and produces a separate, named message for each bad one — the shape of almost every Kubernetes policy you will write at work.

2 · There is no loop. There is a variable.

The path input.spec.template.spec.containers names the whole array. Put a variable where the position would go, and you have asked a different kind of question:

some c in containers does not mean "for each c". It means "for which c?" You are not issuing a command; you are stating a condition with a hole in it, and the engine fills the hole every way it can. Everything odd about Rego iteration follows from that one sentence — so it is the sentence to put on the whiteboard.

This is the same machinery as lesson 1's document-building, seen from the side: a rule body is a query, and a query with a free variable has as many solutions as the data allows. The docs call the variable an output variable¹, because the query hands it back to you filled in.

3 · One rule, one message per offender

Now put it in a rule. The idiomatic spelling declares the variable with some … in:

Read it with lesson 4's model and nothing is new: three expressions, so AND. What is new is that the first expression has three solutions, so the whole body is tried three times — once per binding of c. Two of those tries survive the second expression:

The set does the collecting, exactly as in lesson 2. Each surviving binding adds one member. If two containers had the same name and the same problem, you would get one message, because that is what a set is.

This corrects lesson 4's arithmetic

Lesson 4 told you conftest's N tests counts rule definitions × documents. That held while every definition produced at most one message. It does not survive iteration — above, one definition over one document reports 2 tests. The exact rule, verified over five configurations:

  • failures = the number of messages in the set. That is the honest number.
  • passed = definitions − failures, floored at zero. It is a subtraction, not a measurement.
  • tests = passed + failures.

So an iterating rule that finds three problems reports 3 tests, 0 passed, and the "passed" column silently absorbs the difference. Only the failure count means anything once your rules iterate — which is worth saying out loud to a team that has started putting the summary line in a dashboard.

A policy has one deny definition. It iterates a four-element list and matches three of them. What does the summary line say?

  • Three tests, none of them passed
  • Four tests, only one of them passed
  • One single test, and it failed
  • Four tests, and three of them failed
Failures equals messages, so three. Passed is definitions minus failures floored at zero: 1 − 3 → 0. Tests is their sum, so three. The size of the list you iterated never enters the arithmetic.

4 · Three ways "for loop" will mislead you

The word is close enough to be useful for about a day, and then it costs you. Each of these is a question a coworker will ask, and the answer is the same sentence from section 2.

You will reach forWhat Rego does instead
Order — "it runs first to last" There is no order. The output above proved it: proxy before sidecar. Bindings are solutions to a query, and a solution set has no sequence.
Early exit — break, return Nothing stops. Every binding that satisfies the body contributes a member. You do not get "the first bad container"; you get all of them, which is what a policy report wants anyway.
An accumulator — results.append(…) Nothing accumulates. There is no mutable state in Rego at all¹. You describe what belongs in the set; the engine assembles it.

There is no continue either, and no need for one: a binding whose body fails simply contributes nothing. Skipping is the default, not a statement you write.

5 · The other spellings you will read

Three ways to write the same iteration. All three are current, supported Rego — nothing here is deprecated — but they do not read equally well, and the style guide has a clear default.

_ is an anonymous variable: a hole you never need to refer to again. Form 2 is the same mechanism with the name left out. It is chronologically the older of the two — some … in arrived in OPA v0.34.0 (2021) behind import future.keywords.in and became unconditional in v1.0⁵ — but age is not the argument, and it is worth being precise about that because someone will ask. The wildcard is not deprecated, and Regal does not flag it, even with every rule enabled (verified locally, Regal 0.42.0).

The real argument is ambiguity. The style guide's own reason for preferring form 1 is that brackets are overloaded: "Using the some .. in construct for iteration removes ambiguity around iteration vs. membership checks, and is generally more pleasant to read."⁴ Section 7 below is that overloading in its purest form — on a set, s[x] is a membership test, not a lookup — so containers[_] and roles["admin"] are the same syntax doing two different jobs. some says which one you meant.

Where the wildcard wins outright

The style guide grants form 2 an explicit exception for deeply nested structures⁴, where naming every level is noise:

hostname := data.regions[_].networks[_].servers[_].hostname

# is likely preferable to

some region in data.regions
some network in region
some server in network
hostname := server.hostname

Which is a rule you can hand a coworker as a sentence: name the thing you are going to talk about; leave the levels you are only passing through anonymous. One containers[_] whose element you then use three times wants a name. Three levels of scaffolding on the way to a leaf does not.

Form 3 binds both halves of the pair — for an array that is index, value:

A fourth form is the one to actually avoid: an undeclared named variable in a reference, containers[i].image with no some i. It iterates just the same, and Rego v1 still allows it, but this is the form Regal does flag — use-some-for-output-vars³, verified locally, and the style guide lists message := input.topics[_].body among the accepted fixes for it⁴. That is the sharpest evidence that the wildcard is idiomatic and a bare i is not: with _ the reader can see there is nothing to track, whereas a named i from nowhere could have been bound anywhere above.

6 · Iterating over nothing

Give that rule a document with no containers key — a Service, or a Deployment with the path misspelled:

Undefined collection → zero bindings → zero messages → pass. No error, no warning. This is the fourth distinct way a policy passes a file it should have failed, after lesson 3's missing key and non-main package and lesson 4's undefined sprintf argument. They are all one mechanism wearing four costumes: in Rego, absence is not failure — it is silence.

Flag this one for your coworkers

A rule that iterates a path is only as good as the path. Misspell containers as container and the rule reports a clean pass forever, on every file, for as long as it stays in the repository. The habit from lesson 4 is the answer and it does not change: watch the rule fail on a fixture before you believe it.

7 · Sets have no positions

Lesson 2 left you with "a set is an array without duplicates or order". That is enough to write rules with, and it breaks exactly here, the first time you index one:

So a set has no positions to ask for, and the index/value pair collapses:

Given s := {10, 20, 30}, what does s[1] evaluate to?

  • Undefined, since 1 is absent
  • The number 20, being second
  • The number 10, being first
  • A type error about the index
Brackets on a set test membership and yield the member. There is no member 1, so the expression is undefined — silently, the way every absence in Rego is silent. s[10] would give you 10.

8 · "Any" is free. "All" needs a keyword.

Notice what section 3's rule actually says: there exists a container whose image floats. That existential reading is what iteration gives you for nothing, and it is what a deny rule almost always wants — one message per offender, each naming its offender.

The other quantifier is a separate keyword, every², and it does not fit in a deny body directly: deny wants a reason to fire, and every holds when everything is fine. So it goes in a helper — lesson 4's third OR spelling, doing a new job — and the deny negates it:

Prefer some in a deny rule. The two versions catch the same manifests; only the some version can tell you which container to fix. Reach for every when the requirement genuinely is about the collection as a whole and no single member is at fault.

Two facts about every that will bite someone on your team:

  • It is true of an empty collection. every x in [] { x > 100 } evaluates to true — vacuously, as in every logic system. A workload with zero containers satisfies every rule you can write with it.
  • It is undefined over a missing key, so not every_limited holds. Verified: given a Deployment with container misspelled, the every policy denies it and the some policy passes it. The every version fails closed, which is nicer — but it is a side effect of undefinedness, not a guarantee you designed, and it does not survive the same typo appearing inside the some rule next to it.

Which rule can name the specific container that broke the policy?

  • The one built on some
  • The one built on every
  • Neither of them can do that
  • Both, given sprintf
A some body runs once per binding, so the offending container is bound to a variable and can be interpolated into that binding's message. every yields one verdict about the whole collection, with nothing bound to report.

A coworker writes this to ban privileged containers, tests it against a manifest with one privileged container, and gets a pass. Diagnose it.

deny contains msg if {
	input.kind == "Deployment"
	c := input.spec.template.spec.containers
	c.securityContext.privileged == true
	msg := sprintf("container %s is privileged", [c.name])
}

Then say what the report's summary line will read, and what would have caught it.

Diagnosis: c is bound to the whole array, not to a container. c.securityContext asks an array for a field it does not have, which is undefined, so the body fails — for every input, always. There is no iteration here at all: they wrote := where they needed some c in. Fixing it is one word: some c in input.spec.template.spec.containers.

The summary line: 1 test, 1 passed, 0 warnings, 0 failures, exit 0. One definition, zero messages, so the subtraction reports a pass that never happened.

What catches it: a fixture that must be denied, run before the rule is believed — the same answer as lesson 4, because it is the same failure mode. Worth noticing that this is a fifth costume for the silent pass: not a missing key in the data this time, but a correctly-spelled key asked of the wrong kind of value.

Terminal drill

Twelve minutes. Step 4 is the one to slow down on — predict each summary line out loud before you press return, because that is the skill this lesson is really selling.

  1. Fresh exercise directory. Run from the workspace root.

    mkdir -p exercises/005/policy && cd exercises/005

  2. One fixture with three containers, two of them wrong. Look at the parsed shape before writing any Rego.

    cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  template:
    spec:
      containers:
        - name: app
          image: myco/app:1.4.2
        - name: sidecar
          image: myco/logger:latest
        - name: proxy
          image: nginx:latest
EOF

conftest parse deployment.yaml

  3. The variable, before the rule. Ask the engine the question directly and watch one query return three rows. Then add a filter and watch it return two.

    opa eval -i deployment.yaml \
  'name := input.spec.template.spec.containers[_].name' --format pretty

opa eval -i deployment.yaml \
  'some c in input.spec.template.spec.containers; endswith(c.image, ":latest"); c.name' --format pretty

  4. The rule. Predict the summary line before you run it — how many tests, how many passed.

    cat > policy/images.rego <<'EOF'
package main

deny contains msg if {
	some c in input.spec.template.spec.containers
	endswith(c.image, ":latest")
	msg := sprintf("container %s uses a floating tag: %s", [c.name, c.image])
}
EOF

conftest test deployment.yaml; echo "exit=$?"

  5. Name the position. Rewrite the rule with some i, c in and a %d in the message. Confirm the indexes are the ones you expect, and notice that the printed order still is not document order.

  6. Iterating over nothing. Break the path on purpose, then confirm the damage is invisible.

    sed -i 's/containers$/container/' policy/images.rego
conftest test deployment.yaml; echo "exit=$?"
sed -i 's/container$/containers/' policy/images.rego

  7. The safety error. Write the negation the wrong way round and read the message carefully — it is the one iteration mistake the compiler will catch for you.

    cat > policy/limits.rego <<'EOF'
package main

deny contains "a container has no memory limit" if {
	not input.spec.template.spec.containers[_].resources.limits.memory
}
EOF

conftest test deployment.yaml; echo "exit=$?"

  8. Fix it. Rewrite policy/limits.rego so it binds some c in … first and negates second, with a message naming the container. All three containers should be denied, since none of them sets a limit — so add resources.limits.memory to one of them and confirm the count drops to two.

  9. Sets have no positions. Convince yourself, with no policy file involved.

    opa eval 's := {10, 20, 30}; s[1]' --format pretty
opa eval 's := {10, 20, 30}; s[10]' --format pretty
opa eval 'a := [10, 20, 30]; a[1]' --format pretty

  10. Now yours — no snippet. Write the memory-limit check a second time using every in a helper, keep both versions in the directory, and run them against a manifest where exactly one container is missing a limit. Compare the two reports and say which one you would put in front of a team, and why. Then predict what each does when containers is an empty list — and check. (Ask me if either surprises you.)

Main takeaways

  • A variable in a reference is the loop. some c in xs asks "for which c?" and the engine returns every answer. No order, no break, no accumulator, no continue.
  • A body with a free variable is evaluated once per binding, so one rule definition can add many members to the set — one message per offender, each naming it.
  • Three spellings, all current: some c in xs (the default), xs[_] (compact, and preferred for deeply nested paths), some i, c in xs (when the position belongs in the message). The wildcard is not deprecated and Regal does not flag it; some is preferred because brackets are ambiguous between iteration and membership. An undeclared named variable is the one Regal rejects.
  • Conftest's count changes meaning once a rule iterates: failures = messages; passed = definitions − failures, floored at zero. Only the failure count is measured.
  • Iterating a missing or misspelled path yields zero bindings and a clean pass — the fourth silent pass in this course. Absence is silence, not failure.
  • Negating an iterating expression is a compile error (rego_unsafe_var_error). Bind with some first, negate second.
  • On a set, s[x] is a membership test yielding x, not indexing: {1,2,3}[2] is 2. In some i, v in, a set's key is its value.
  • every supplies "for all", usually via a helper the deny negates. It is vacuously true on an empty collection, undefined on a missing one, and it cannot name the member that broke the rule.

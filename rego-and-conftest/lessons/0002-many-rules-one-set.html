Rego & Conftest · Lesson 2

Many Rules, One Set

A real policy has to say several things at once. One keyword — contains — turns a pile of independent rules into a single collected answer. This is the shape every policy you write at work will have.

Your win for this lesson

By the end you can write a policy that collects every problem with an input into one set of messages, explain why a passing check produces an empty set rather than nothing at all, and say out loud the one sentence that makes contains obvious to a coworker.

Lesson 1 left you with a rule that answers one question with one value: allow is true, or the key is absent. That is a complete rule, and it is the right tool for a yes/no verdict.

But the verdict is not what a person needs. When your pipeline rejects a config, the useful output is not false — it is the list of things that are wrong. All of them, in one pass, so the author fixes everything before pushing again.

1 · Why a complete rule cannot do this

The obvious first attempt is to write two rules with the same name, each producing a message. Try it and Rego stops you:

This is not a limitation to work around. It is the docs being strict about a promise: "Documents produced by rules with complete definitions can only have one value at a time… If evaluation produces multiple values for the same document, an error will be returned."¹ A key in a JSON document holds one value. Two rules claiming that key is a genuine contradiction, and OPA refuses to pick a winner.

So the fix is not to make the rules quieter. It is to change what kind of thing the key holds: not one message, but a collection of them — where "two rules both had something to say" is normal rather than contradictory.

2 · contains: each rule adds one member

Swap := for contains and the same three rules cooperate instead of colliding. This is the whole lesson:

A rule written this way is a partial set rule — the docs also call it a multi-value rule. Each definition is a partial, incomplete description of the final key; put together, they complete it. The reference word is incremental: "the rule definition is called incremental because each definition is additive."¹

rule 1
body holds
→ adds its message
rule 2
body holds
→ adds its message
rule 3
body fails
→ adds nothing
→
violations
one set, two members

Read a line right to left and it says itself. violations contains M if B means: when B holds, M is in violations. Nothing is being appended, ordered or looped over — the rule is a standing claim about what belongs in a set.

The sentence to put on the whiteboard

A complete rule answers "what is the value?" — so a second answer is a contradiction.
A partial set rule answers "what belongs?" — so a second answer is just another member.

Same file, same syntax, same if. The only difference is whether the key holds an answer or the answers.

Two violation := complete rules both fire on the same input. What happens?

  • Evaluation stops with a conflict
  • The document keeps both messages
  • The final rule quietly wins
  • The earliest rule quietly wins
A complete rule's key can hold exactly one value, so two rules claiming it is a contradiction and OPA errors out rather than choosing. That error is the signal that you wanted contains.

3 · Run it and read the set

A sixteen-year-old with no username breaks two of the three rules:

Two rules fired and both contributed. The third — the empty-username check — did not, because the key is absent rather than empty. Every problem reported at once, which is exactly what the person fixing the config needs.

Sets have no JSON equivalent, so OPA serialises them as arrays on the way out. Inside Rego it is still a set: unordered, no duplicates. The square brackets in that output are a printing detail, not a promise about order.

4 · A clean input gives you an empty set, not nothing

Now fix both problems and re-run. Predict the output before you read on — the interesting part is not the values but whether the key is there.

This is the structural difference from lesson 1, and it is worth pausing on. When a complete rule's body failed, the key vanished — {}, undefined. When every partial set rule fails, the key is still there, holding nothing.

A partial set rule is always defined. Zero contributions is a perfectly good answer to "what belongs?" — the answer is "nothing". So a passing policy does not produce silence; it produces [].

That property is what makes this shape usable by a pipeline. The caller never has to distinguish "no violations" from "the policy did not load" — it can simply count:

Decision versus enforcement, again: Rego computed 0. Deciding that 0 means "let the merge through" is the caller's job.

Every rule body fails for a clean input. What is data.signup.violations?

  • an empty set, still present
  • undefined, so the key vanishes
  • the boolean false, always present
  • null, meaning nothing was added
Zero contributions is a valid outcome for a set, so the key exists and holds no members. This is what a pass looks like — and it is why callers can just count the set instead of testing for undefined.

5 · The set is a set: duplicates and order are gone

Two rules can legitimately produce the same message. Because the key holds a set, the second contribution is absorbed:

Set semantics also mean rule order in the file is meaningless — you can reorder, split across files, or delete one rule without touching the others. That independence is the practical payoff: adding a new check is always append a rule, never edit a function.

6 · The trap: a rule that adds nothing looks exactly like a pass

Here is the failure mode that will bite your team. Feed the policy an input with no age key at all:

Nothing is broken; the policy did precisely what it was told. input.age is undefined, so the comparison is undefined, so the body does not hold, so the rule contributes nothing — and "contributes nothing" is indistinguishable from "found no problem". You can watch it happen directly:

Flag this one for your coworkers

A missing key does not make a check fail — it makes the check disappear. This is lesson 1's undefined arriving in its dangerous form: a policy that silently approves everything it cannot see. Absent data must be its own rule, which is exactly why the example needs both not input.username (key absent) and input.username == "" (key present but empty). They are different bugs and neither one catches the other.

So the discipline is: for every field you check, decide what "missing" means. Sometimes absence is fine. When it is not, write the not rule too — as the username checks do.

The input has no age key. The age rule…

  • adds nothing, because the comparison is undefined
  • adds its message, because absent means zero
  • raises an error, because the key is missing
  • adds its message, because absent means false
Referring to an absent key yields undefined, and an undefined expression cannot satisfy a body — so the rule contributes no member. No error, no message: a silent pass.

7 · Where this is heading

You have just written the shape of every policy you will write at work. A real conftest policy is this file with a different name for the key and a work-shaped condition in the body:

The name violations was arbitrary; nothing in Rego cares. Conftest will later insist on deny, violation or warn, because a wrapper needs a convention to look for. That convention is all conftest adds here — the mechanism is the contains you just learned.

Check yourself

Which line adds one message to a set named violations?

  • violations contains "too young" if input.age < 18
  • violations := "too young" if input.age < 18
  • violations[_] == "too young" if input.age < 18
  • contains violations "too young" if input.age < 18
The rule name comes first, then contains, then the member it adds. The := version is valid Rego but a complete rule — it sets the key to that one string, and a second such rule would conflict.

A coworker asks: "why is our policy's output an empty list when everything passes? Shouldn't it just say OK?" Answer them in two or three sentences.

The policy's output is a set of problems found, built by rules that each add one message when they have something to report. When nothing is wrong, no rule contributes, so the set is empty — and empty is the answer, not the absence of one. The pipeline then just counts: zero members means pass.

If your answer used the words "returns" or "checks", nudge it back toward "builds" and "belongs". The rules are not running checks and reporting; they are describing what belongs in a set.

Terminal drill

Ten minutes. Steps 4 and 6 are the ones that matter — one shows you the empty set, the other shows you the silent pass.

  1. Fresh directory beside your lesson-1 work. Run this from the workspace root.

    mkdir -p exercises/002-partial-set-rules && cd exercises/002-partial-set-rules

  2. First, meet the error on purpose. Write the two-complete-rules version and run it, so the conflict message is one you have seen rather than one you have read about.

    cat > conflict.rego <<'EOF'
package conflict

violation := "age must be at least 18" if input.age < 18

violation := "username is required" if not input.username
EOF

echo '{ "age": 16 }' > input.json
opa eval -d conflict.rego -i input.json 'data.conflict' --format pretty

  3. Now the working version. Type it rather than pasting — contains is the keyword you want in your fingers.

    cat > policy.rego <<'EOF'
package signup

violations contains "age must be at least 18" if input.age < 18

violations contains "username is required" if not input.username

violations contains "username can't be empty" if input.username == ""
EOF

opa eval -d policy.rego -i input.json 'data.signup' --format pretty

  4. The empty set. Make the input valid and re-run. Say out loud why the key is still there, when lesson 1's allow key disappeared.

    echo '{ "age": 21, "username": "meleu" }' > input.json
opa eval -d policy.rego -i input.json 'data.signup' --format pretty
opa eval -d policy.rego -i input.json 'count(data.signup.violations)' --format pretty

  5. Separate the two username rules. Predict which message you get for each input before running it — that is the retrieval, not the typing.

    echo '{ "age": 21, "username": "" }' > input.json
opa eval -d policy.rego -i input.json 'data.signup.violations' --format pretty

echo '{ "age": 21 }' > input.json
opa eval -d policy.rego -i input.json 'data.signup.violations' --format pretty

  6. The silent pass. Drop the age key entirely and watch the policy approve it. Then find the exact expression that went undefined.

    echo '{ "username": "meleu" }' > input.json
opa eval -d policy.rego -i input.json 'data.signup' --format pretty
opa eval -d policy.rego -i input.json 'input.age < 18' --format pretty

  7. Now fix it yourself — no snippet given. Add a fourth rule that reports a missing age, then confirm the previous input no longer passes. (Ask me if it fights back.)

  8. Last, prove set semantics to yourself. Add a rule contributing a message another rule already contributes, and count the members.

    opa eval --format pretty 'x := {"zebra", "apple", "apple", "mango"}'

Main takeaways

  • A complete rule (:=) holds one value; two of them firing at once is a conflict error, not a merge.
  • A partial set rule (contains) collects members. Each definition is incremental — additive, independent, order-free.
  • Read it as: violations contains M if B → when B holds, M belongs to violations.
  • Complete rules answer "what is the value?"; partial set rules answer "what belongs?"
  • A partial set rule is always defined. Zero contributions gives [] — that is what a pass looks like, and why callers can count().
  • Sets deduplicate and have no order; OPA prints them as arrays because JSON has no set type.
  • A missing key makes a check disappear, not fail. If absence matters, write a not rule for it.

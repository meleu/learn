Rego & Conftest · Lesson 4

AND Down, OR Sideways

Rego has no and keyword and no or keyword. It does not need them: stacking expressions inside one body is AND, and repeating the rule name is OR. That is the whole logic system, and it is the last structural thing you need before your policies stop being one-liners.

Your win for this lesson

You close lesson 3's open debt — the missing input.kind guard — and write a rule whose message names the offending value, which needs both halves of today's model at once.

1 · Two operators, spelled with layout

Every other language you know spells these with words. Rego spells them with position:

deny contains msg if {
  • input.kind == "Deployment"
  • input.spec.replicas < 2
}
OR
deny contains msg if {
  • input.kind == "StatefulSet"
  • input.spec.replicas < 2
}

Read down a column and you are reading AND. Read across the columns and you are reading OR. The docs say both outright — "The rule body can be understood intuitively as: expression-1 AND expression-2 AND … AND expression-N"¹, and "When you join multiple expressions together in a query you are expressing logical AND. To express logical OR in Rego you define multiple rules with the same name."²

AND goes down. OR goes sideways. Six words, and it is the entire control flow of the language. Put it on the whiteboard before you write a single rule in front of your team — almost every "why doesn't my policy fire?" question is someone who has stacked alternatives where they meant to spread them.

You already use the OR half without calling it that. Lesson 2's three violations contains … rules and lesson 3's three deny rules were sideways all along: independent definitions of one name, each contributing to one set. The docs call this incremental definition¹ — new today is only that you may use it on alternatives for the same message, not just on different messages.

Three things about bodies that are worth knowing now:

  • Order does not change the result. A body is a conjunction, not a sequence — shuffle those two lines and the same files fail. Order is for the human: lead with the guard so a reader knows the subject before the predicate.
  • A one-expression rule is the same thing. deny contains "…" if expr is a body with one member. Lesson 3's rules were not a different form; they were short.
  • The separator is a newline (a ; also works on one line, and opa fmt will rewrite it into newlines).

Flag this one for your coworkers

The guard is a filter, not an assertion. input.kind == "Deployment" inside a deny body does not mean "the file must be a Deployment" — it means "ignore this file unless it is one". Somebody will eventually write a rule that is silently skipped for every file in the repository because its guard names a kind that never appears, and the report will happily say 0 failures.

If any value inside that sprintf is undefined, the sprintf is undefined, so the expression does not hold, so the whole rule contributes nothing — even though the two checks above it both held. Verified: a one-replica Deployment with no metadata.name passes this policy, silently.

$ conftest test noname.yaml

1 test, 1 passed, 0 warnings, 0 failures, 0 exceptions

This is lesson 3's Trap A with a new face: an absent key now sabotages a rule from the message rather than from the condition. Interpolate keys you are confident exist (kind, metadata.name) and be deliberate about the rest.

A body has three expressions. The first two hold, the third is undefined. What does the rule contribute?

  • Nothing at all, silently
  • Its message, exactly once
  • A hard error, loudly
  • An empty string member
A body is an AND: one undefined expression makes the whole body fail to hold, and a rule whose body does not hold contributes no member. There is no partial credit and no error.

The habit that catches it is the same one that catches everything else here — write the failing fixture first and confirm the rule actually rejects it. A rule you have never watched fail is a rule you have not written yet. (A later lesson turns that habit into committed tests with conftest verify.)

6 · Two shorter spellings of the same OR

Two columns that differ only in one literal is a lot of duplicated body. When the alternatives are just values, put the OR inside the expression with a set and in:

When the alternatives are conditions rather than values, name the OR with a helper rule — a plain complete rule, defined twice, holding no message and belonging to no convention:

The helper is not a new mechanism. It is sideways-OR again, given a name so the guard reads as a noun and can be reused by every rule in the file. Note what it evaluates to:

Choosing between the three: differ by a value → in a set; differ by a condition, used once → two definitions; differ by a condition, used more than once → a helper. All three are the same operator wearing different clothes, so this is a readability call, not a correctness one.

That matches the advice in Styra's own guide to the question⁴: helper rules are the idiomatic default, and in is for a one-off check of known values — if you catch yourself repeating the same in, promote it to a helper. Note that "two definitions of deny" and "a helper" are not rival techniques; the second is the first, given a name.

That guide lists five further ways to express OR, which is worth knowing exists before a coworker arrives having read it. Two are worth a sentence here. else chains rule bodies in a fixed evaluation order — real, but it buys ordering you almost never need, and it does not apply to a partial set rule like deny at all. default supplies a fallback value when every definition is undefined — also inapplicable here, and for a reason you already know: a partial set rule is always defined, because contributing nothing yields an empty set. Both belong to complete rules, which is why neither appears in a conftest policy.

You want one message for either of two unrelated conditions. What do you write?

  • Two rules with one name
  • Two lines in one body
  • Two names in one rule
  • One rule with two heads
Repeating the rule name is how Rego spells OR; both definitions contribute to the same set. Two lines in one body would be AND, and would require both conditions to hold at once.

What does a helper rule such as is_workload evaluate to when its bodies all fail?

  • Undefined, so it never holds
  • False, which is a value
  • An empty set, always defined
  • An error about that rule
A complete rule with no default is undefined when every definition's body fails. Undefined does not hold, so a body referencing it fails — which is exactly the behaviour you want from a guard.

A coworker shows you this and says "it never fires, and I have checked the YAML ten times."

deny contains msg if {
	input.kind == "Deployment"
	input.metadata.namespace == "default"
	input.metadata.namespace == "kube-system"
	msg := sprintf("%s is in a reserved namespace", [input.metadata.name])
}

Diagnose it, fix it two different ways, and say what would have caught it before review.

Diagnosis: the two namespace lines are an AND, not a list of alternatives. They ask for one string to equal "default" and "kube-system" simultaneously, so the body can never hold — for any input. Everything about the run looks healthy: it compiles, it is counted in the report, and it always passes.

Fix one — sideways. Two definitions of deny, identical but for the namespace literal.

Fix two — inside the expression. The alternatives are only values, so input.metadata.namespace in {"default", "kube-system"}, and the rest of the body is unchanged. (A helper, reserved_namespace if … defined twice, is a third fix and the right one once a second rule needs the same test.)

What catches it: a fixture that must be denied, run before the rule is believed. A rule nobody has seen fail is unverified — and a dead rule is invisible in a report that only counts what ran.

Terminal drill

Twelve minutes. Step 5 is the one to slow down on — you want to have written the dead rule yourself, once, deliberately.

  1. Fresh exercise directory. Run from the workspace root.

    mkdir -p exercises/004/policy && cd exercises/004

  2. Three fixtures: two that must fail, one that must be ignored.

    cat > deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
spec:
  replicas: 1
EOF

cat > statefulset.yaml <<'EOF'
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  replicas: 1
EOF

cat > service.yaml <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  ports:
    - port: 80
EOF

  3. AND. The guarded rule, then prove the guard works by watching the Service pass a rule it has no business satisfying.

    cat > policy/replicas.rego <<'EOF'
package main

deny contains "Deployment must have at least 2 replicas" if {
	input.kind == "Deployment"
	input.spec.replicas < 2
}
EOF

conftest test deployment.yaml; echo "exit=$?"
conftest test service.yaml; echo "exit=$?"

  4. The message joins the AND. Swap the literal for a sprintf, then delete metadata.name from a copy of the Deployment and watch the rule go quiet. Predict the report before you run it.

    cat > policy/replicas.rego <<'EOF'
package main

deny contains msg if {
	input.kind == "Deployment"
	input.spec.replicas < 2
	msg := sprintf(
		"%s/%s has %d replicas; at least 2 required",
		[input.kind, input.metadata.name, input.spec.replicas],
	)
}
EOF

conftest test deployment.yaml

printf 'apiVersion: apps/v1\nkind: Deployment\nspec:\n  replicas: 1\n' > noname.yaml
conftest test noname.yaml; echo "exit=$?"

  5. The dead rule. Write the mistake on purpose, confirm the toolchain says nothing, then check the count you get for three files.

    cat > policy/dead.rego <<'EOF'
package main

deny contains "workload has fewer than 2 replicas" if {
	input.kind == "Deployment"
	input.kind == "StatefulSet"
	input.spec.replicas < 2
}
EOF

opa check policy/; echo "opa check exit=$?"
conftest test deployment.yaml statefulset.yaml service.yaml
rm policy/dead.rego

  6. OR. Fix it properly: append a second definition of deny for StatefulSets. Both fixtures must now fail, and the Service must still pass.

    cat >> policy/replicas.rego <<'EOF'

deny contains msg if {
	input.kind == "StatefulSet"
	input.spec.replicas < 2
	msg := sprintf(
		"%s/%s has %d replicas; at least 2 required",
		[input.kind, input.metadata.name, input.spec.replicas],
	)
}
EOF

conftest test deployment.yaml statefulset.yaml service.yaml; echo "exit=$?"

  7. Collapse it. Rewrite the two definitions as one rule using in. Same two failures, different count — say why out loud before you look.

  8. Name it. Rewrite again with a replicated_workload helper defined twice, then inspect the helper directly for a Deployment and for the Service.

    conftest parse service.yaml > service.json
opa eval -d policy/replicas.rego -i service.json 'data.main' --format pretty

Main takeaways

  • AND goes down, OR goes sideways. Expressions in one body are conjoined; definitions sharing a rule name are disjoined. There are no and/or keywords.
  • A guard is a first expression that filters which documents the rule speaks about — input.kind == "Deployment". It is not an assertion about the file.
  • Body order does not affect the result. Lead with the guard for the reader.
  • msg := sprintf(fmt, [args]) is an expression in the AND: an undefined value inside it silences the whole rule, checks and all.
  • Stacking mutually exclusive equalities produces a dead rule — compiles, counts, never fires. Not opa check, not conftest, not even Regal catches it. Only a failing fixture does.
  • Three spellings of one OR: in a set for one-off value checks, two definitions for conditions, a helper rule for conditions used more than once. Styra's guide lists eight; else and default are not among the ones that apply to deny.
  • Conftest's N tests counts rule definitions × documents; helper rules are not counted.

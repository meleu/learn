Lesson 01 · Knowledge

The key pass actually uses

You already have a GPG key and a password store. This lesson does not create anything — it opens the box you already own and shows you that nothing inside it is magic.

The reason pass felt uncomfortable is not that its commands are hard. Its commands are trivial. The discomfort comes from handing real credentials to a layer you cannot see into. So we start there: by the end of this page you will be able to point at a specific line of gpg output and say that is the key protecting my passwords — and then prove it from the ciphertext itself.

One asymmetry, and everything follows. The public key locks a secret. The private key unlocks it. That is the whole trick. It means pass insert never needs your passphrase — writing a secret only requires the public half — while pass show always does.

If you have ever wondered why pass insert is instant but pass show pops a pinentry prompt: this is why. Adding is a public operation. Reading is a private one.

Step one: read your own key

Run this. The flags matter — the defaults hide exactly the things we care about.

terminal

$ gpg --list-keys --with-subkey-fingerprints --keyid-format=long

You will get something shaped like this. The key IDs will be yours, not these — every hex string on this page is a fabricated example:

pub   ed25519/4C7B1E9A05D3F268 2026-01-15 [SC]
      A3F92D1B7C4E60885B0D2A944C7B1E9A05D3F268
uid                 [ultimate] Ada Byron <ada@example.com>
sub   cv25519/D82A6F14B90C7E35 2026-01-15 [E]
      61B45E8027FA3D19C6E08B72D82A6F14B90C7E35

Five lines, four ideas. Take them one at a time — and if a word here is unfamiliar, the glossary defines all of them in one place.

LineWhat it is
pub The primary key, public half. This is your identity in OpenPGP terms. Everything else in the block hangs off it.
ed25519/2DA6…9007 Algorithm, then the long key ID — a 16-hex-digit handle for the key.
the 40-hex line The fingerprint: the full, unambiguous name of the key. Look closely — the key ID above is simply its last 16 characters.
uid A user ID: the human label bound to the key. [ultimate] is how much you trust it, and you made it, so: ultimately.
sub A subkey. A second, separate keypair, cryptographically bound to the primary. Note its algorithm and fingerprint are entirely different.

You typed gpg --full-generate-key once and got two keypairs. That surprise is the first thing to clear up.

Step two: the bracketed letters are the whole story

[SC] and [E] are not decoration. They are the key's capabilities — what GPG is permitted to use each key for. GnuPG ships the legend on your own disk, at /usr/share/doc/gnupg/DETAILS:

LetterCapabilityMeans
CCertifyCan vouch for keys and user IDs — including its own subkeys.
SSignCan produce signatures proving you wrote something.
EEncryptCan have data locked to it.
AAuthenticateCan prove identity to a service, e.g. as an SSH key.

So your primary key certifies and signs. It cannot encrypt. Your subkey does exactly one thing: encrypt. GnuPG's own manual is blunt about this — "by default a primary key has no encryption capability."

Why split them at all?

Because the two jobs have different lifetimes. The primary key is your permanent identity — losing it means losing the name. The encryption subkey is a working tool: it can be revoked and replaced without you becoming a different person. That separation is why every GPG hygiene guide talks about subkeys, and it is the thing that will let you rotate keys later without rebuilding your store's identity.

Step three: prove which key holds your passwords

Here is the claim: pass encrypts to the [E] subkey, not to the primary key you named. Do not take my word for it. Your store names its recipient by email address:

terminal

$ cat ~/.password-store/.gpg-id
ada@example.com

An email address — no key ID anywhere. Now ask the ciphertext itself who it was locked to. --list-only means GPG parses the packets without decrypting, so this needs no passphrase:

terminal

$ gpg --list-packets --list-only ~/.password-store/email/fastmail.gpg
:pubkey enc packet: version 3, algo 18, keyid D82A6F14B90C7E35

Try this on any file in your store. Every one of them will name the same subkey. If a file ever names a key ID you do not recognise, someone else can read it — which is precisely the check you will use in the team-sharing lesson.

Read that key ID again, then look back at your key listing. It is D82A6F14B90C7E35 — the sub … [E] line. Not 4C7B1E9A05D3F268. The chain runs like this:

.gpg-id
an email address
→
keyring lookup
finds the uid that matches
→
primary key
[SC] — cannot encrypt
→
encryption subkey
[E] — the actual recipient

That resolution — friendly name to primary key to capability-matched subkey — is GPG doing its job silently, and it is the single most common source of "wait, which key is this?" confusion. You have now watched it happen.

Retrieval practice

Answer before scrolling back. Getting one wrong here is worth more than getting it right by peeking.

You run pass insert github. Which key does GPG encrypt that file to?

  • The subkey flagged [E], for encryption
  • The primary flagged [SC], for signature
  • The userid flagged [full], for trusting
  • The keygrip flagged [SSB], for storage
The primary key has no encryption capability at all. GPG walks from the name in .gpg-id to the primary key, then down to a subkey that can actually do the job.

gpg --list-secret-keys prints a line beginning ssb. What is that?

  • A secret subkey held on disk
  • A signed statement held on disk
  • A stored session held on disk
  • A secret backup held on disk
sec/ssb are the private-half spellings of pub/sub. Same two keys, listed from the side that can decrypt.

4C7B1E9A05D3F268 and A3F92D…4C7B1E9A05D3F268: what is the relationship?

  • The short one ends the long one
  • The short one hashes the long one
  • The short one signs the long one
  • The short one seeds the long one
A long key ID is just the last 16 hex digits of the fingerprint — an abbreviation, nothing more. The fingerprint is the real name; prefer it whenever you are telling a machine which key you mean.

You ran one gpg command and got two keypairs. Why does GPG do that, and which one would you have to replace if your laptop were stolen?

The two keys have different jobs and different lifetimes. The primary ([SC]) is your durable identity: it certifies, and replacing it means becoming a new person to everyone who knows your key. The subkey ([E]) is the working part that data is actually encrypted to, and it is designed to be revocable and replaceable without disturbing the identity.

After a laptop theft you would revoke and replace the encryption subkey, keeping the primary — but only if the primary was not sitting on the stolen machine too. On a standard single-machine setup it is. That gap is exactly what the offline-primary ceremony exists to close, and why it is worth knowing about even while we skip it.

Do it on your own machine

Nothing here changes any state. Run all four and read the output rather than skimming it.

  1. Run gpg --list-keys --with-subkey-fingerprints --keyid-format=long and say out loud which line is the primary and which is the subkey.
  2. Run the same command with --list-secret-keys instead. Confirm you get sec/ssb where you had pub/sub, and the same key IDs.
  3. Pick any secret in your store and inspect its packets: gpg --list-packets --list-only "$(find ~/.password-store -name '*.gpg' | head -1)". Find the keyid and match it against your listing by eye.
  4. Repeat for a file in a different subdirectory of your store. Confirm it names the same subkey.
  5. Run gpg --list-keys --with-colons and find scESC on the pub line and e on the sub line. That is the machine-readable form of the capability letters.

Check this before you trust any backup guide

Run ls ~/.gnupg. If there is no pubring.kbx, your GnuPG is running the newer keyboxd backend, which keeps public keys under public-keys.d/ instead. This is the default on GnuPG 2.4+ installs. It matters because a great many GPG backup guides tell you to copy pubring.kbx, and on such a system that advice silently backs up nothing. We will do backup properly, with --export rather than file copying, in the lesson on creating your real key.

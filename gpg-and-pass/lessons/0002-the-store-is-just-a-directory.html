Lesson 02 · Knowledge + Skill

The store is just a directory

In lesson 01 you named the key that protects your passwords. Now we open the other black box: pass itself. By the end you will have read a secret out of your store without pass involved at all.

The fear that keeps people off pass is rarely stated out loud, but it is always the same one: if this tool breaks, or stops being maintained, or I end up on a machine without it, are my credentials gone? That is a completely reasonable thing to want an answer to before you trust it with anything real.

The answer is short. pass is a single Bash script — 720 lines on this machine, and you can read the whole thing over a coffee. It stores each secret as one ordinary GPG-encrypted file in an ordinary directory tree. Everything else it does is convenience.

pass show x/y is gpg -d ~/.password-store/x/y.gpg. Not "similar to". The same operation, reached by a shorter name. Once you have seen that with your own eyes, pass stops being a thing you trust and becomes a thing you understand.

Step one: look at it on disk

No pass subcommand here. Just look:

terminal

$ find ~/.password-store -not -path '*/.git/*'
/home/you/.password-store
/home/you/.password-store/.gpg-id
/home/you/.password-store/email
/home/you/.password-store/email/fastmail.gpg
/home/you/.password-store/work
/home/you/.password-store/work/aws
/home/you/.password-store/work/aws/prod.gpg

Compare that to pass ls, which prints the same tree with .gpg trimmed off and some colour added. That is genuinely all pass ls is: tree with a suffix filter.

Two structural facts fall out of that listing, and both matter more than they first appear.

ObservationConsequence
One secret = one file The store is git-friendly, rsync-friendly and find-friendly by construction. A merge conflict can only ever involve one secret.
Filenames are not encrypted Anyone who can read the directory learns that you have an account at work/aws/prod — just not the password. Encrypted contents, plaintext metadata. Name your entries with that in mind.

This is a real design trade-off, not an oversight. It is what lets the store be browsable, greppable and mergeable. If leaking the shape of your credentials is unacceptable for a given secret, that secret needs a different home.

Now ask the filesystem what one of those files actually is:

terminal

$ file ~/.password-store/email/fastmail.gpg
…/fastmail.gpg: PGP ECDH Public-Key Encrypted Session Key - keyid: D82A6F14 B90C7E35

A standard OpenPGP message. Not a pass format — there is no such thing as a pass format. And note the key ID it names: the [E] subkey from lesson 01.

Step two: prove the equivalence, both directions

First direction — read a secret without pass. Run both and diff them:

terminal

$ diff <(pass show email/fastmail) <(gpg -q -d ~/.password-store/email/fastmail.gpg) && echo IDENTICAL
IDENTICAL

Byte for byte. You have just recovered a credential with a tool that predates pass by fifteen years.

Second direction is the one that really settles it — write a secret without pass, then read it back with pass:

terminal

$ mkdir -p ~/.password-store/work/aws
$ echo 'made-by-raw-gpg' | gpg -e -r ada@example.com -o ~/.password-store/work/aws/prod.gpg

$ pass show work/aws/prod
made-by-raw-gpg

pass never noticed. There is no index, no database, no manifest to keep in sync — a file that appears in the tree is an entry, immediately, because the tree is the only state there is.

The recovery recipe, in one loop

This is the answer to "what if pass disappears". It needs a shell and gpg, and nothing else:

$ find ~/.password-store -name '*.gpg' | while read -r f; do
    name="${f#$HOME/.password-store/}"
    printf '%s: %s\n' "${name%.gpg}" "$(gpg -q -d "$f" | head -1)"
  done
email/fastmail: hunter2
work/aws/prod: made-by-raw-gpg

Worth keeping somewhere you will find it in a bad week. It is written up in Reference 02.

Step three: .gpg-id and the nearest-ancestor rule

One file in that tree is not encrypted: .gpg-id. It is a plain list of recipients, one per line, and it is how pass decides who a new secret gets locked to.

The rule is the only piece of pass logic worth memorising, and it is exactly the rule you already know from .gitignore or .editorconfig: walk up from the secret's directory and use the first .gpg-id you hit. Here it is in the source, lightly trimmed:

/usr/bin/pass — set_gpg_recipients()

local current="$PREFIX/$1"
while [[ $current != "$PREFIX" && ! -f $current/.gpg-id ]]; do
        current="${current%/*}"
done
current="$current/.gpg-id"

So a store with two .gpg-id files resolves like this:

work/aws/prod
no .gpg-id in aws/
→
work/.gpg-id
found — stop here
✕
store root
never consulted

That single rule is the whole basis of scoped access: give work/ its own .gpg-id and everything beneath it is encrypted to a different set of people than the rest of the store. pass init -p work grace@example.com writes that file and re-encrypts everything below it, printing what it touched:

terminal

$ pass init -p work grace@example.com
Password store initialized for grace@example.com (work)
work/aws/prod: reencrypting to 7524A409FDB1733C

Verify it the way you learned in lesson 01 — ask the ciphertext, not the tool:

terminal

$ gpg --list-packets --list-only ~/.password-store/work/aws/prod.gpg | grep keyid
:pubkey enc packet: version 3, algo 18, keyid 7524A409FDB1733C   # grace's [E] subkey

$ gpg --list-packets --list-only ~/.password-store/email/fastmail.gpg | grep keyid
:pubkey enc packet: version 3, algo 18, keyid D82A6F14B90C7E35   # still ada's

The team lesson is built entirely on this one mechanism. For now it is enough to know the rule and be able to predict, for any file in the tree, which .gpg-id governs it.

The trap this creates

mv and pass mv are not interchangeable, and this is the one place where "it's just files" will bite you. Move a secret across a .gpg-id boundary with plain mv and the file lands in its new directory still encrypted to the old recipients — the tree says one thing, the ciphertext says another, and nothing warns you. pass mv re-encrypts on arrival. Use it.

Step four: what the wrapper actually adds

Everything so far has argued that pass is a thin shell over gpg. True — but thin is not nothing, and one of the flags it passes is load-bearing. Line 9 of the script:

/usr/bin/pass — line 9

GPG_OPTS=( $PASSWORD_STORE_GPG_OPTS "--quiet" "--yes" "--compress-algo=none" "--no-encrypt-to" )

--no-encrypt-to tells GPG to ignore any encrypt-to line in your gpg.conf. That option, if you have ever set it, silently adds a recipient to everything you encrypt. Watch the difference on a store whose .gpg-id names only Ada, with encrypt-to grace@example.com sitting in gpg.conf:

terminal

$ echo secret | gpg -e -r ada@example.com -o /tmp/raw.gpg
$ gpg --list-packets --list-only /tmp/raw.gpg | grep keyid
:pubkey enc packet: version 3, algo 18, keyid D82A6F14B90C7E35   # ada  — asked for
:pubkey enc packet: version 3, algo 18, keyid 7524A409FDB1733C   # grace — did NOT ask for

$ printf 'secret\n' | pass insert -m -f email/test
$ gpg --list-packets --list-only ~/.password-store/email/test.gpg | grep keyid
:pubkey enc packet: version 3, algo 18, keyid D82A6F14B90C7E35   # ada, and only ada

Raw gpg quietly encrypted to a second person. pass did not. So the honest version of this lesson's thesis is: the store is just files and you can always read it by hand — but when you write to it by hand, you are opting out of a guarantee. .gpg-id is the recipient list only because pass refuses to let anything else join it.

This is also why the recovery loop above is a read recipe. Reading by hand is free. Writing by hand is a decision.

Retrieval practice

A secret sits at work/aws/prod. There is a .gpg-id in the store root and another in work/. Which applies?

  • Only the nearer file, in work
  • Only the higher file, at root
  • Both of the files, once merged
  • None of the files, until reinit
pass walks up from the secret's own directory and stops at the first .gpg-id it finds. Nearest ancestor wins, and the ones above it are never read.

You copy a .gpg file into your store by hand, using cp. What does pass ls show?

  • The new entry, listed immediately
  • The new entry, after reindexing
  • An error, about unknown entries
  • Nothing, until you reinsert it
There is no index to update. The directory tree is the only state pass has, so pass ls is reading the filesystem live.

Someone reads your password store directory but has none of the private keys. What do they learn?

  • Which accounts you hold, not the passwords
  • Which accounts you hold, and the passwords
  • Neither the accounts held, nor the passwords
  • Not the accounts held, but the passwords
Contents are encrypted; filenames are not. The pass-name work/aws/prod is readable by anyone who can list the directory — which is worth remembering before you push the store to a shared git remote.

A colleague says: "I don't want to depend on pass — what happens to my passwords if the project dies?" Answer them in a few sentences, and name the one thing your answer does not cover.

Every secret is a standalone OpenPGP file in a plain directory tree, so any secret can be read with gpg -d alone, and the whole store with a three-line find … | while read loop. pass is a Bash script you can read in an afternoon; nothing about the on-disk format depends on it existing. The dependency is on GPG and on your private key, not on pass.

What it does not cover: writing. Hand-rolled gpg -e honours encrypt-to in gpg.conf and does not consult .gpg-id at all, so a hand-written entry can end up with recipients you did not intend and did not see. Losing pass costs you nothing on the read path and real guarantees on the write path.

Do it on your own machine

Steps 1–4 are read-only and safe against your real store. Step 5 builds a throwaway store in /tmp — PASSWORD_STORE_DIR is how you experiment without risking anything.

  1. Run find ~/.password-store -not -path '*/.git/*' and then pass ls. Satisfy yourself that they are the same tree.
  2. Pick any entry and run the diff: diff <(pass show NAME) <(gpg -q -d ~/.password-store/NAME.gpg). Expect silence.
  3. Run the recovery loop from the green box above against your real store. This is the command you want muscle memory for.
  4. Run cat ~/.password-store/.gpg-id, then find ~/.password-store -name .gpg-id. If there is more than one, name which entries each governs before checking.
  5. Build a scratch store and reproduce step two's second direction — write with raw gpg, read with pass: 
    $ export PASSWORD_STORE_DIR=/tmp/scratch-store
$ pass init YOUR_EMAIL
$ mkdir -p "$PASSWORD_STORE_DIR/demo"
$ echo hello | gpg -e -r YOUR_EMAIL -o "$PASSWORD_STORE_DIR/demo/hand-made.gpg"
$ pass ls
$ pass show demo/hand-made
    Then unset PASSWORD_STORE_DIR and rm -rf /tmp/scratch-store.
  6. In that same scratch store, run sed -n '80,90p' /usr/bin/pass and read the while loop that implements the nearest-ancestor rule. Five lines. That is the feature.

Where this is going

You can now name your key, prove which key any file is encrypted to, and recover the entire store without the tool that made it. That is the whole "is this safe to trust" question answered — and it is the point at which the practice key has done its job.

Next we throw it away and build the real one deliberately: expiry, a revocation certificate, and a backup taken with --export rather than by copying files that may not exist on your system.

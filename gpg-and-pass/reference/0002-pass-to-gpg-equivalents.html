pass ↔ gpg

What each pass subcommand does underneath, and how to get your secrets back with no pass on the machine. Print this one.

Recover the whole store without pass

find ~/.password-store -name '*.gpg' | while read -r f; do
    name="${f#$HOME/.password-store/}"
    printf '%s: %s\n' "${name%.gpg}" "$(gpg -q -d "$f" | head -1)"
done

Needs a shell, gpg, and your private key. Nothing else. Drop | head -1 to print full multiline entries. Redirect to a file only if you have somewhere safe to put plaintext — and prefer piping straight into whatever consumes it.

Command equivalents

Paths below assume the default store; $PASSWORD_STORE_DIR overrides it.

passUnderneathNotes
pass ls tree ~/.password-store Strips the .gpg suffix, prunes .git.
pass show x/y gpg -d ~/.password-store/x/y.gpg Exactly equivalent. Verify with diff <(…) <(…).
pass show -c x/y gpg -d … | head -1 | wl-copy Plus a background job restoring the previous clipboard after $PASSWORD_STORE_CLIP_TIME (45s default).
pass insert x/y gpg -e -r $(cat .gpg-id) -o x/y.gpg Not equivalent — see the write-path warning below.
pass generate x/y N tr -dc "$charset" < /dev/urandom → insert Character set set by -n / $PASSWORD_STORE_CHARACTER_SET.
pass grep RE gpg -d each file → grep Decrypts everything in turn. Slow on a big store, and it never touches disk.
pass mv a b mv + re-encrypt if needed Plain mv across a .gpg-id boundary leaves the old recipients in place. Always use pass mv.
pass rm x/y rm ~/.password-store/x/y.gpg Plus a git commit if the store is a repo. Note the history keeps the ciphertext.
pass init -p d ID… write d/.gpg-id + re-encrypt below it Re-encryption needs your private key: you must be able to read what you rewrite.
pass git … git -C ~/.password-store … Plus a diff.gpg.textconv config so git diff shows plaintext.

Which key is this file encrypted to?

terminal

# no passphrase needed — parses packets without decrypting
gpg --list-packets --list-only FILE.gpg | grep keyid

# audit the entire store at once
find ~/.password-store -name '*.gpg' -exec sh -c \
  'printf "%s " "$1"; gpg --list-packets --list-only "$1" | sed -n "s/.*keyid \(.*\)/\1/p" | tr "\n" " "; echo' _ {} \;

The IDs you see are [E] subkey IDs, not primary key IDs. Match them against gpg --list-keys --with-subkey-fingerprints --keyid-format=long. An ID you cannot account for means someone else can read that file.

The .gpg-id resolution rule

For a secret at a/b/c, pass checks in order and stops at the first hit:

  1. a/b/.gpg-id
  2. a/.gpg-id
  3. .gpg-id (store root)

Nearest ancestor wins; the ones above it are never read and never merged. Recipients are one per line, by uid or fingerprint; # starts a comment. Source: set_gpg_recipients() in /usr/bin/pass.

Reading by hand is free. Writing by hand is not.

pass encrypts with --no-encrypt-to, which makes GPG ignore any encrypt-to line in your gpg.conf. Hand-rolled gpg -e does not: it will silently add that recipient, and it never consults .gpg-id at all. If you must write by hand, mirror the full option set from line 9 of the script:

gpg -e --quiet --yes --compress-algo=none --no-encrypt-to \
    $(sed 's/#.*//;/^$/d;s/^/-r /' ~/.password-store/x/.gpg-id) \
    -o ~/.password-store/x/y.gpg

Then verify the recipients came out right with the --list-packets command above.

Things the store does not hide

Filenames, directory structure, file sizes and modification times are all plaintext. Anyone with read access to the directory — or to a git remote you pushed it to — learns which accounts you hold and roughly when you last changed each one. Only the contents are encrypted.
